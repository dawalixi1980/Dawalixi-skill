# canvas-skill — Canvas 架构图契约执行器

## 定位

**通用**的 canvas 契约执行器，与具体项目无关。适用于任意 `.canvas` 架构图 / 工作流连接器。

## 这个 skill 解决什么

canvas（`.canvas`）是给人看的**可视化图**，对模型是「一段含转义换行的 text 字段」。模型常见失误：

- 把 `text` 节点当**辅助说明**，只读个大概，漏掉其中整条规则；
- 只看主干连线，漏掉**支链**；
- 忽略 `group` 的 **label 语义**（例如把「全局约束」当成普通框）；
- 忽略 **边 label**（它往往是条件或产出说明）；
- 见到 `file` 节点不去打开，凭印象自拟结构；
- 用自己设计的产物替换掉 canvas 指定的产出；
- canvas 标了 `xxx（skill）` 却**只读说明、不实际调用**。

本 skill 的职责：**把 canvas 机械翻译成可执行契约，并用核对表强制逐节点执行。**

## 触发时机

出现下列任一情况立即加载本 skill：

- 用户提到「架构图 / 架构 / canvas / 连接器 / 工作流图 / 流程图 / 按架构 / 根据架构」；
- 消息或上下文出现 `@xxx.canvas`、`.canvas` 文件名；
- 任务是多阶段流水线，且用户强调「连接器」「一步一步」「按节点」。

## 执行协议（强制，按序）

### 第 0 步：解析，不要肉眼读 JSON

```bash
node "<skill_dir>/scripts/parse_canvas.cjs" "<canvas 文件绝对路径>"
```

输出包含：分组、节点清单（text 全文展开）、连线（含 label）、拓扑执行序、**skill 调用清单**、自动告警。

若脚本不可用，退化为手工解析，且**必须**逐项列出：所有 `group`（label＋成员）、所有 `text` 节点（**全文原文**）、所有 `file` 节点、所有 `link` 节点、所有 `edge`（含 label）。

### 第 1 步：先输出「节点核对表」，再动手

在开始任何实际工作前，先输出如下表格（**未输出即视为违规**）：

| # | 节点/连线 | 类型 | 契约要求（原文摘要） | 完成判据 | 状态 |
|---|---|---|---|---|---|
| 1 | `A → B` | edge | 从 A 产出交给 B | B 消费了 A 的产出 | ⬜ |

规则：

- **每个 `text` 节点一行**（哪怕它看起来像注释）；
- **每个 `file` 节点一行**，且必须实际打开读取；
- **每个 `group` 一行**，声明其约束作用范围；
- **每条 `edge` 一行**，label 当作条件/产出写入「契约要求」。

### 第 2 步：按拓扑序逐节点执行

- 严格按解出的「拓扑执行序」推进；同层可并行。
- 每完成一个节点，把它在核对表里标为 `✅` 并附**一句依据**（读了哪个文件、产出什么）。
- 阶段产出**不得替换** canvas 指定的产出物名称与来源。

### 第 3 步：全局约束贯穿

- `group` label 含「全局 / 约束 / 规则」的，其内部指令对**每一个**阶段生效。
- 含「一步一步 / 每步确认 / 与用户互动」的指令：**每个阶段结束必须停下等待用户确认**，禁止连做多阶段。

### 第 4 步：skill 调用规则（强制）

**规则一：canvas 点名 skill，就必须调用。**

- 节点文字中出现 skill 标记的（`（skill）`、`(skill)`、`skill：xxx`、`使用 xxx skill` 等），一律视为**强制调用指令**。
- **只读该 skill 的说明文档、不实际执行其流程，等同于未执行该节点**（高频失分点）。
- 调用前先加载对应 skill，调用后必须产出该 skill 定义的产物。

**规则二：必须按「连线维度」调用，即按工作流位置调用。**

skill 在 canvas 中的位置不是建议，是**时序与数据流的约束**：

- **入边 = 输入**：该 skill 的输入必须来自它的所有入边节点。若 `模板 → 清洗（skill）`，则清洗对象必须是「模板」，不得换成其他资料或凭空生成。
- **出边 = 产出与去向**：产出的形态与用途由出边决定，且必须真的被下游使用，不得产出后弃用。
- **位置 = 时序**：只能在 canvas 将其放置的那一步调用；不得提前、延后、合并、跳过，不得把串行改成并行。
- **边 label = 约束条件**：带 label 的边是调用该 skill 时必须满足的条件。

**规则三：维度一致。**

skill 的产出维度必须与 canvas 上该节点声明的维度一致——声明是「文段/参考」就产出可供参考的文段，声明是「转换」就产出转换件，不得降级为「看一眼说明」。

**规则四：一次调用＝一次核对。**

每次调用 skill 后，在核对表中追加一行：`skill 名称 | 所在步骤号 | 入边输入 | 出边产出 | 状态`。

### 第 5 步：收尾自检

- 输出完整核对表，确认无 `⬜`；
- 对被判定「不适用」的节点，写明理由；
- 若 canvas 存在**环、孤立节点、悬空连线、无 label 的边**，明确指出并请求用户裁决。

## 示例（示意，非某个具体项目）

若 canvas 形如：

```
[知识库] --→ [资料目录]
[资料目录] --→ [规则文件.md]
[模板目录] --→ [清洗（skill）] --→ [生成大纲]
[规则文件.md] --→ [生成大纲]
[生成大纲] --→ [使用者确认] --→ [逐章生成] --→ [确认后合并] --→ [格式转换（skill）]
group「全局约束」: [必须与使用者互动] [一步一步来]
```

正确执行意味着：清洗 skill 的输入取自「模板目录」、产出交给「生成大纲」；规则文件.md 必须被打开并按规则执行；「全局约束」两条对每个阶段生效；每一步结束停下等待确认。任何"只读说明不调用""自拟结构替换产出""一步到位"都属违规。

## 反模式（务必避免）

1. ❌ 只读 canvas 主干，跳过**支链**。
2. ❌ 见到 `file` 节点不打开，**自拟结构/产物**。
3. ❌ 把「全局约束」分组当成普通说明框。
4. ❌ 漏掉「每级标题都要…」「每章都要…」这类**逐级/逐项**要求。
5. ❌ 把「一步一步来」当作建议而非硬门禁，一次推进到底。
6. ❌ 把 `text` 节点里的大段规则当"背景"跳过。
7. ❌ canvas 标了 `xxx（skill）`，只读说明文档就当作已完成，**没有实际调用**。
8. ❌ 在**错误的步骤**调用 skill（提前/延后/合并/跳过），或产出不交给出边节点、产出后弃用。
9. ❌ 调用 skill 时**换了输入来源**（不用入边节点作为输入，改用自己想当然的资料）。

## 与其他 skill 的关系

本 skill 只负责**解析与强制**，不代替图中引用的具体 skill。正确做法是：本 skill 解析出「该用哪个 skill、在第几步用、输入输出是什么」，再去调用对应 skill。

## 注意

- canvas 里的 `text` 常含 Markdown（`#` 标题、`>` 引用、`**粗体**`），解析后按其原始语义执行，不要降级成普通句子。
- 若 canvas 与某个 `file` 节点内容冲突：**以文件内容为准**，并把冲突报告给用户。
- 节点顺序与连线是权威；不要用「看起来更合理」的流程替换图中的流程。
