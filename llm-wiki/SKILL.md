# LLM Wiki — 个人知识库构建模式

一种使用 LLM 构建个人知识库的实践模式。

> 基于 [Andrej Karpathy 的 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。

## 核心理念

与传统的 RAG（每次查询都检索）不同，LLM **增量式地构建和维护一个持久的 Wiki**——一个结构化、相互关联的 Markdown 文件集合。当你添加新的资料来源时，LLM 会读取它，提取关键信息，并将其整合到现有的 Wiki 中——更新实体页面、修订主题摘要、标注矛盾之处、强化不断演进的综合知识。

**Wiki 是一个不断积累的持久化成果。** 交叉引用已经存在，矛盾已被标记，综合知识反映了你阅读过的所有内容。每增加一份资料、每提出一个问题，Wiki 都会变得更加丰富。

你永远不需要亲自编写 Wiki——LLM 负责编写和维护全部内容。你只需要负责搜集资料、探索和提出正确的问题。

## 架构（三层）

### 1. 原始资料层
你精心收集的源文档集合——文章、论文、图片、数据文件。这些是**不可变的**。LLM 可以读取它们，但从不修改它们。这是你的事实依据。

### 2. Wiki 层
LLM 生成的 Markdown 文件目录——摘要、实体页面、概念页面、对比分析、概览、综合汇总。LLM 全权负责这一层：创建页面、在新资料到来时更新、维护交叉引用、保持一切一致性。**你读它，LLM 写它。**

### 3. 模式层
一份配置文件（即本 Skill），告诉 LLM Wiki 的结构、约定和工作流程。你和 LLM 一起随时间共同演进这个文件。

## 操作流程

### 资料摄入
用户放入新资料。LLM 执行以下操作：
1. 读取资料并讨论关键要点
2. 在 Wiki 中写入摘要页面（包含完整的导航，遵循[[#链接规则]]）
3. 更新[[#总纲索引]]——将新页面添加到树状结构中，附带可点击的链接
4. 更新 Wiki 中相关的实体和概念页面——添加双向链接
5. 在日志中追加一条记录

一份资料可能会触及 10-15 个 Wiki 页面。建议一次只摄入一份资料以保证质量。

### 查询
向 Wiki 提问。LLM 执行以下操作：
1. 读取 `[index.md](../index.md)`，通过树状结构找到相关页面
2. 读取这些页面（跟随导航栏中的超链接）
3. 综合答案，附带指向源页面的可点击引用链接
4. **优秀的答案会被归档回 Wiki 中成为新页面**——对比分析、关联挖掘等不应丢失在对话历史中

### 检查（健康检查）
定期对 Wiki 做健康检查，关注：
- 页面之间的矛盾
- 被新资料取代的过时观点
- 没有入链的孤立页面
- 被提及但没有独立页面的重要概念
- 缺失的交叉引用
- **断链**——搜索 `](./xxx.md)` 模式并验证每个目标文件是否存在
- **单向链接**——对于页面 A 上的每个 `[text](./B.md)`，验证页面 B 是否有返回 A 的链接
- 可以通过网络搜索填补的数据缺口

## 默认位置（工作区感知 — 关键）

Wiki 必须存放在**用户资料和项目所在的位置**，而不是隐藏在全局文件夹中。按以下优先级确定位置：

1. **项目/工作区目录（首选）。** 如果用户在项目文件夹内指定了资料（例如"把这里面的资料做成 wiki"且文件在 `G:\剧本\`），或者当前工作区包含源文件，则在**该项目内**创建 Wiki——通常是 `<项目>/wiki/`。这样 Wiki 就紧邻其资料，并位于用户可能已有的任何 Obsidian 仓库内。
2. **已有的 Wiki 位置。** 如果项目中已存在包含 `WIKI-SCHEMA.md` 的 `wiki/`（或 `wiki-knowledge/`）目录，则复用它——切勿在其他位置创建第二份副本。
3. **用户显式指定的路径。** 如果用户指定了具体目录，则使用它。
4. **全局兜底（最后手段）。** 仅当完全没有项目上下文时才回退到 `~/.workbuddy/wiki-knowledge/`——例如用户丢了一个 URL 或引用了分散在不相关位置的文件，且明确想要一个全局知识库。

**Obsidian 感知。** 如果项目目录中存在 `.obsidian/` 文件夹，说明用户正在那里运行 Obsidian 仓库。Wiki 必须放在该仓库内，以便图谱视图和搜索功能可见。不要把它埋在 `~/.workbuddy/` 下。

**永远不要将资料与 Wiki 分离。** 不要将 Wiki 写入 `~/.workbuddy/` 而资料却放在项目文件夹中——这会使 Wiki 对用户和他们的仓库不可见。如果对位置有疑问，请**询问**用户；不要默默地使用全局路径。

## 入门指南

当用户想要创建 Wiki 时，按以下步骤操作：

### 第一步：初始化结构
在**项目目录内**创建（资料文件所在的位置，通常是 Obsidian 仓库——参见[[#默认位置（工作区感知 — 关键）]]）。元文件（`index.md`、`log.md`、`WIKI-SCHEMA.md`）放在项目根目录以便可见；源文件放入 `raw/` 子文件夹（不可变存档）；内容页面放在 `wiki/` 子文件夹中，**按主题文件夹组织**——绝不要扁平堆放：
```
<项目>/                      # 项目根目录 (= Obsidian 仓库)
├── raw/                      # 不可变的源文件存档
│   └── <源文件>.md           # 原始源文档（只读）
├── index.md                  # 总纲索引（分层导航）— 元文件，位于根目录
├── log.md                    # 按时间顺序的操作日志 — 元文件，位于根目录
├── WIKI-SCHEMA.md            # 模式与约定 — 元文件，位于根目录
└── wiki/                     # LLM 维护的内容页面
    ├── 索引-<分类>.md         # 分类索引页（每个主题一个）
    ├── <分类文件夹>/          # 主题文件夹 — 将相关页面分组
    │   ├── [页面].md
    │   └── <子文件夹>/        # 子主题文件夹（如 人物档案/）
    │       └── [页面].md
    ├── <分类文件夹2>/
    └── ...
```
**为什么要用文件夹？** 人类读者按分类导航，而不是扁平列表。文件夹分组镜像了 Obsidian 文件资源管理器的工作方式——折叠/展开、层层深入、视觉过滤。每个内容页面必须属于一个主题文件夹（`wiki/` 根目录下的分类索引页除外）。

**规则**：`raw/` 对 LLM 是只读的——你只能从 `raw/` 读取源文件，绝不能修改或删除。当用户引入新的源文档时，先放入 `raw/`，然后从它创建 Wiki 页面。

### 第二步：创建 index.md
Wiki 中所有内容的目录——每个页面都带有链接、一行摘要和元数据（日期、资料数量）。按分类组织。LLM 在每次摄入时更新它。

**规模规则（阈值：20 页）。** 当 Wiki 超过 20 个内容页面时，将 `index.md` 转换为**分层导航**模式：
1. `index.md` 仅列出分类标题，每个标题链接到 `wiki/索引-<分类名>.md` 中对应的分类索引页
2. 每个分类索引页列出该分类下的所有页面，包含描述和交叉引用
3. `index.md` 顶部增加一个"快速检索"区——常用查询的关键词到页面的映射表
4. 20 页阈值是一个指导原则，不是硬性限制——根据判断：如果用户在 25 页时仍偏好扁平模式，就保持扁平；如果用户在 18 页时就需要分层，就分层。默认 20 页以下扁平，20 页及以上分层。

### 第三步：创建 log.md
仅追加的按时间顺序记录。每条记录的格式：
```markdown
## [YYYY-MM-DD] 操作类型 | 标题
简要描述做了什么。
```
使用一致的前缀，以便用 grep 解析：
```bash
grep "^## \[" log.md | tail -5
```

### 第四步：创建 WIKI-SCHEMA.md
描述以下内容的配置文件：
- 目录结构和约定
- 页面格式模板
- 交叉引用规则
- 领域特定分类
- 资料摄入/查询/检查的工作流程

根据用户的特定领域对此进行定制。

## 链接规则（关键 — 每个页面都必须遵守）

所有链接使用**标准的 Markdown 相对路径**——绝不使用裸的 `[[wiki-links]]`。
标准 Markdown 链接在任何查看器（GitHub、VS Code、Obsidian 等）中都能工作。

**跨目录前缀（基于文件夹的布局）。** 当元文件位于项目根目录而内容页面位于 `wiki/` 下的主题文件夹中时，每个链接的前缀取决于*当前文件的文件夹深度*：

| 当前文件位于 | 到根目录 (index/log/schema) | 到 raw/ | 到同级页面（同文件夹） | 到同级文件夹 |
|---|---|---|---|---|
| `wiki/<分类>/页面.md` | `../../index.md` | `../../raw/x.md` | `./页面.md` | `../<同级>/页面.md` |
| `wiki/<分类>/<子类>/页面.md` | `../../../index.md` | `../../../raw/x.md` | `./页面.md` | `../../<同级>/页面.md` |

通用规则：统计 `../` 的数量 = 从 `wiki/` 到文件的目录层级数 + 1。
- 分类索引页（在 `wiki/` 根目录）：到根目录 = `../index.md`，到 raw = `../raw/x.md`，到内容页 = `./<分类>/页面.md`

### 1. 导航栏（每个页面必须）
每个页面必须在标题后立即以导航栏开始：
```markdown
> **导航**: [← 返回总纲](../index.md) | [相关页面A](./页面A.md) | [相关页面B](./页面B.md)
```

### 2. 行内交叉引用（在内容中）
当提到另一个页面或概念时，使用行内链接：`[岗位113](./岗位113-经营部技术人员.md)`

### 3. 子项锚点链接
当引用另一个页面中的特定章节时，使用章节锚点：
```markdown
[笔试 — 土木工程知识](./笔试备考指南.md#二土木工程专业知识备考)
```
章节锚点使用标题文本，全小写，空格替换为连字符，以 `#` 为前缀。

### 4. 底部导航（每个页面必须）
每个页面必须以包含指向所有相关页面的链接的"相关页面"章节结束：
```markdown
## 相关页面
- [← 返回总纲](../index.md)
- [页面1](./页面1.md) — 说明
- [页面2](./页面2.md) — 说明
```

### 5. 总纲索引要求
`index.md` 是 Wiki 的入口点：
- **扁平模式（< 20 页）**：树状大纲，每个 Wiki 页面都链接并描述
- **分层模式（≥ 20 页）**：仅列分类标题，每个标题链接到分类索引；顶层索引保持简洁
两种模式都需要：
- 反映逻辑关系的层级结构
- 每个链接必须可点击
- 索引必须包含指向主要页面关键子章节的链接

### 6. 双向链接
对于从页面 A 到页面 B 的每个链接，页面 B 也必须有返回页面 A 的链接。
使用[[查询链接]]来验证不存在断链或单向链接。

## 页面格式模板

```markdown
---
title: 页面标题
type: entity | concept | source-summary | comparison | synthesis
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [源文件名列表]
tags: [相关标签]
---

# 页面标题

> **导航**: [← 返回总纲](../index.md) | [相关页1](./页面1.md) | [相关页2](./页面2.md)

此处为内容。使用 `[链接文本](./目标文件.md)` 进行交叉引用。
子章节使用：`[链接文本](./目标文件.md#章节名称)`

## 相关页面
- [← 返回总纲](../index.md) — 返回知识库总目录
- [页面1](./页面1.md) — 简短说明
- [页面2](./页面2.md) — 简短说明
```

## 使用场景

| 领域 | 原始资料 | Wiki 页面 |
|------|----------|-----------|
| **个人** | 日记条目、文章、播客笔记 | 目标、健康追踪、自我提升 |
| **研究** | 论文、文章、报告 | 实体、概念、不断演进的论点 |
| **读书** | 章节笔记 | 角色、主题、情节线索 |
| **工作** | Slack 线程、会议记录、文档 | 内部知识库 |
| **竞品分析** | 公司报告、新闻 | 竞争对手档案、对比分析 |
| **课程笔记** | 讲义、阅读材料 | 主题摘要、概念图谱 |

## 小贴士

- **Obsidian** 是非常好的 Wiki 查看器——图谱视图显示关联，Dataview 插件可查询 frontmatter 元数据
- **Wiki 就是一个 Markdown 文件的 Git 仓库**——免费获得版本历史、分支和协作功能
- **Marp** 可以从 Wiki 内容生成幻灯片
- **Web Clipper**（Obsidian 插件）将网页文章转换为 Markdown，方便资料摄入
- **将图片下载到本地**以确保持久性——设置一个固定的附件目录

## 重要原则

1. **原始资料不可变**——绝不修改源文档
2. **LLM 拥有 Wiki**——用户阅读，LLM 编写和维护
3. **知识复利增长**——每次摄入和查询都在丰富 Wiki
4. **归档好答案**——不要让有价值的分析消失在对话中
5. **定期检查**——随着 Wiki 增长，保持其健康状态
